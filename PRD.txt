## 1 — EXECUTIVE SUMMARY

WorldGaming is a production-grade sports betting platform built entirely on Cloudflare's edge infrastructure, designed for operators running private books across Cricket, Football, Tennis, and Volleyball. It is purpose-built for markets where near-zero latency odds delivery, granular per-user risk controls, and instant account administration are not optional — they are the baseline expectation of every serious player.

The current sportsbook software market is dominated by white-label solutions that were architected for centralized server deployments, not edge compute. Platforms such as BetConstruct, EveryMatrix, and SBTech carry the structural debt of traditional three-tier web applications: centralized WebSocket hubs that become bottlenecks during live match spikes, database architectures that cannot handle concurrent high-volume bet placement without queueing delays, and admin panels that rely on role hierarchies too rigid for agent-based operator models. None of these platforms are deployable on Cloudflare Workers natively — they require dedicated VMs, load balancers, and regional databases that add cost, complexity, and latency.

Phase 1 of WorldGaming delivers five production-ready modules: the User Betting Frontend, the Realtime Live Match Engine, the Wallet and Ledger System, the Admin Panel at `/sgyt`, and the Risk and Fraud Engine. This scope proves the core value proposition — sub-50ms odds delivery to any user globally via Cloudflare Durable Objects, backend-only session authentication with instant account revocation, and a double-entry ledger that maintains financial integrity at any concurrency level. Payment gateway integration, self-service registration, and advanced analytics dashboards are deliberately deferred to Phase 2 so the engineering team can validate the realtime infrastructure under live match load before adding complexity.

## 2 — PRODUCT VISION AND GOALS

### 2.1 Vision Statement

WorldGaming is the edge-native operating system for private sportsbook operators — a single platform where admins create accounts, set limits, manage odds, and settle markets without touching a server.

### 2.2 Mission

WorldGaming gives sportsbook operators complete control over their user base, markets, and financial exposure through a Cloudflare-native stack that eliminates infrastructure management, delivers live odds in under 50ms globally, and enforces risk rules at the API layer before a single rupee changes hands.

### 2.3 Core Product Goals

- **Deliver sub-50ms odds to every connected client** — leverage Cloudflare Durable Objects as per-match WebSocket hubs broadcasting updates to all subscribers simultaneously, with zero additional infrastructure.
- **Enforce zero-trust session security** — store all session state in Cloudflare KV as opaque tokens; enable admin-triggered instant lockout by deleting the KV record, with no JWT residual window.
- **Guarantee ledger integrity at any concurrency level** — use atomic database transactions for every wallet operation so balance = sum of all transactions at all times, with no partial-write corruption possible.
- **Support per-user risk controls set by the admin** — every user record carries individual max-bet, max-bet-per-day, max-win-per-day, and allowed-sports limits enforced at the API layer before bet acceptance.
- **Enable real-time risk visibility for operators** — admin dashboard shows live liability by market, live exposure by user, and incoming bet flow in real time via AdminBroadcast Durable Object.
- **Maintain immutable audit history** — every admin action (odds change, wallet credit, user suspend, bet void) is written to both D1 and Cloudflare R2 as an append-only NDJSON log that cannot be deleted via the API.
- **Handle live match traffic spikes without pre-scaling** — Cloudflare Workers auto-scale to handle 50,000+ concurrent WebSocket connections per live match; no operator intervention required during India vs Pakistan matches.

### 2.4 Design Principles

- **Backend-only authentication** — the client holds zero auth logic, zero permission checks, and zero decoded user data beyond what the API explicitly returns. All access decisions happen in Hono middleware on the Worker.
- **Edge-first, server-last** — hot data (odds, market state, sessions, suspension flags) lives in KV and Durable Objects at the edge. The primary database (PlanetScale) is the system of record, not the critical path.
- **Atomic money, always** — no wallet mutation occurs outside a database transaction. `balance_before` + `amount` = `balance_after` on every ledger row, verifiable at any point in time.
- **Fail closed on suspension** — any bet placement attempt on a suspended market, by a suspended user, or with a frozen wallet receives an explicit rejection before the DB write. KV suspension flags are checked before any DB operation.
- **Operator control before user convenience** — account creation, deposit approval, withdrawal processing, and betting enablement are all operator-gated. User self-service exists only for actions that carry no financial or security risk (e.g., viewing bet history, updating display preferences).

## 4 — MARKET CONTEXT AND COMPETITIVE POSITIONING

### 4.1 Problem Statement

The private sportsbook market — operators running books for known user pools rather than public-facing regulated bookmakers — is structurally underserved by existing platform software. Most operators use WhatsApp-based ledgers, Excel sheets, or low-quality script-kiddie sportsbook PHP panels that have no concept of real-time odds, WebSocket delivery, or atomic wallet transactions. The platforms that do exist at enterprise level (BetConstruct, EveryMatrix, SBTech) are built for licensed, publicly facing operators and are priced and architected accordingly — minimum deals in the range of $50K–$200K setup fees, running on traditional VMs with rigid deployment requirements.

The specific structural weakness shared by all existing platforms is their WebSocket architecture. Every major competitor runs a centralized WebSocket server (often a Node.js cluster behind a load balancer) that becomes a bottleneck during high-concurrency live match events. During an India vs Pakistan T20, a centralized WS server handling 50,000 concurrent connections requires pre-provisioned infrastructure, active monitoring, and manual scaling decisions. Cloudflare Durable Objects eliminate this entirely — one DO per match, auto-deployed to the edge, scales to 100K connections with no operator intervention.

The second structural weakness is authentication and session management. PHP-based sportsbook panels often store sessions in Redis or database tables with no instant revocation mechanism. If an operator needs to ban a user mid-match, the user's existing session may remain valid for 15–30 minutes due to JWT TTLs or session cache TTLs. WorldGaming's KV-backed opaque token architecture makes account suspension instant — deleting a KV key revokes access on the next request.

### 4.2 Competitive Landscape

| Competitor | Strengths | Weaknesses |
|---|---|---|
| **BetConstruct** | Mature product, large market coverage, regulatory licensing tools | Enterprise-only pricing, centralized WS architecture, no edge deployment, rigid user management |
| **EveryMatrix** | Strong odds feed integrations, modular products, white-label flexibility | High setup cost, traditional server deployment, no real-time admin dashboard with live DO-level performance |
| **SBTech (now part of Golden Nugget / DraftKings)** | Strong US sports coverage, tech depth | Not available to private operators; US-market focused |
| **Script-based PHP panels (ClubHouse, etc.)** | Low cost, easy install | No real-time odds, no atomic wallets, severe security vulnerabilities, no audit trail, no scalability |
| **Sportradar / Betradar** | Gold-standard data feeds, global coverage | Data provider only — no betting platform; requires integration work |

### 4.3 Positioning Statement

WorldGaming combines Cloudflare Durable Objects-powered sub-50ms live odds delivery with backend-only atomic session management — neither of which any single sportsbook platform in the private-operator segment currently delivers together.

## 6 — FEATURE REQUIREMENTS [P0] — BETTING PLATFORM (USER FRONTEND)

### 6.1 Overview

The User Betting Frontend is the primary interface for all registered betting users. It is served from Cloudflare Pages as a React 18 SPA and communicates with the Hono API on Cloudflare Workers. All session state is managed server-side via KV-backed opaque tokens; the client holds no auth logic. The frontend exists in Phase 1 to convert the admin's match and odds configuration into an interactive betting surface that delivers live odds via WebSocket and processes bet placements through the atomic bet lifecycle.

### 6.2 Account & Session

- Users may only log in with credentials issued by an admin; no self-registration endpoint exists.
- On login, the Worker validates credentials, generates a 256-bit random opaque token, writes it to `SESSIONS` KV namespace with a 24-hour TTL, and sets an HttpOnly, Secure, SameSite=Strict cookie named `sess_token`.
- The client receives only `{ userId, username, balance }` in the login response; no role data, no token value.
- Session TTL slides on every authenticated request (refreshed to 24h from last activity).
- If a user's account is suspended by an admin, the KV session record is deleted; the user's next request returns HTTP 401 and the client redirects to the login page.
- Login history is visible to the user — displaying device, IP country, and timestamp for the last 10 successful logins.
- Account status (Active / Suspended / Betting Disabled) is displayed in the user header on all authenticated pages.

### 6.3 Sports Lobby & Navigation

The sports lobby is the authenticated home page of the platform. It displays all configured active sports with a top navigation tab per sport. Below the sport tabs, events are grouped by league and sorted by start time ascending. Each event card shows home team, away team, start time, top 3 market odds (match winner or equivalent), and a live badge if the match status is `live`.

Supported sports in Phase 1: Cricket, Football, Tennis, Volleyball.

Navigation structure:
1. Sports tab bar (Cricket / Football / Tennis / Volleyball).
2. League grouping within the selected sport.
3. Event cards within each league.
4. Clicking an event card opens the Match Detail page.

The favourites system allows users to star specific events; starred events appear in a Favourites tab that is the default view on the lobby. Search allows querying active events by team or league name.

### 6.4 Bet Slip

The bet slip is a persistent sidebar on desktop and a bottom-sheet drawer on mobile. It maintains user selections across page navigation without requiring a persistent connection — selection state is stored in Zustand client state and survives SPA route transitions.

Bet slip behaviour:

1. User clicks an odds button on any market — the selection is added to the bet slip.
2. If the same selection is clicked again, it is removed (toggle off).
3. Clicking a different selection in the same market replaces the existing selection for that market within an accumulator.
4. Each selection row shows: event name, market name, selection name, current odds, a stake input field, and potential payout.
5. Quick stake buttons (₹100, ₹500, ₹1,000, ₹5,000, and a custom input) are available below each stake input.
6. If the selection's odds change while it is in the bet slip, the odds value flashes green (if increased) or red (if decreased) for 2 seconds, and the potential payout recalculates automatically.
7. If the selection's market is suspended while it is in the bet slip, the selection row displays a `SUSP` badge in amber, the stake input is disabled, and the Place Bet button is blocked.
8. Accumulator (multi-bet) mode: when two or more selections are in the bet slip, a parlay row appears below the singles showing the combined odds and combined potential payout based on a single entered stake.
9. Before submission, a bet confirmation modal shows: selections, stake, odds, and estimated payout. User must confirm.
10. On submission, if a bet delay is configured for the market (e.g., live in-play), a countdown modal is shown. During the countdown, odds are rechecked. If odds change beyond threshold, the user is notified and must re-confirm or cancel.

### 6.5 Cricket Live Scoreboard

The cricket scoreboard is displayed on the Match Detail page for live cricket events. It receives updates in real time from the MatchDO WebSocket connection established when the user opens the match page.

Components:

- Ball-by-ball live ticker — six-ball over displayed as coloured dot notation (dot, 1, 2, 3, 4, 6, W, WD, NB).
- Live scorecard — batting: batsman name, runs, balls, 4s, 6s, SR; bowling: bowler name, overs, maidens, runs, wickets, economy.
- Partnership stats — current partnership runs and balls.
- Fall of wickets timeline — dismissal event log with over and score.
- Run rate comparison — current RRR vs CRR as a horizontal bar chart.
- Live win probability bar — home team win % vs away team win %, updated after each ball.
- Wagon wheel visual — Phase 2 (deferred; requires additional WebGL rendering work outside core scope).

### 6.6 Football Live Match Display

- Live match timeline — chronological event log (kickoff, goals, yellow/red cards, substitutions, half-time, full-time) as a vertical timeline on the match page.
- Score ticker — live score in large type with match minute counter updating every 60 seconds via WebSocket.
- Goal events with scorer name.
- Card events with player name and minute.
- Substitution events with players in/out.
- Match statistics panel — possession, shots on target, corners, fouls (updated every 5 minutes from API feed).
- Lineups display — starting XI and substitutes for both teams, shown pre-match and during.

### 6.7 Tennis Live Display

- Game/Set/Match score hierarchy — current game score (e.g., 40-15), current set score (e.g., 5-4), match sets (e.g., 1-0).
- Point-by-point feed — chronological point-by-point ticker with server indicator.
- Break point indicator — visual badge when a break point is in play.
- Set history — all completed set scores displayed.
- Serve speed and ace counter — available where API feed provides this data.

### 6.8 Volleyball Live Display

- Set-by-set scoreline — current set score and historical set scores.
- Point-by-point within current set — real-time point ticker.
- Timeout indicators — visual badge when a team has called a timeout.
- Team momentum indicator — running 5-point differential trend.

### 6.9 Betting History

- All Bets tab — paginated list of all user bets across Open, Settled, and Cancelled/Void statuses.
- Each bet row shows: bet ID, event name, market, selection, stake, odds, status badge, and settled amount.
- Clicking a bet row expands to the Bet Detail view: full bet breakdown including placement timestamp, acceptance timestamp, settlement timestamp, and settlement outcome.
- Filter controls: by sport, by market type, by date range, by status.
- Running P&L display at the top of the Betting History page — total staked, total returned, net P&L for the selected filter period.

### 6.10 Notifications

Notifications are delivered in two channels:

1. **WebSocket push** — immediate, in-session delivery of: bet settled (win/loss), odds changed on slip selection, market suspended, cashout available, account notices from admin.
2. **In-app notification centre** — persistent inbox of all notifications stored in the DB, accessible via a bell icon in the header. Unread count badge.

## 7 — FEATURE REQUIREMENTS — REALTIME [P0] & LIVE MATCH ENGINE

### 7.1 Overview

The Realtime Engine is the core infrastructure that differentiates WorldGaming from all polling-based sportsbook platforms. It uses Cloudflare Durable Objects as per-match WebSocket hubs, feed ingestion Workers for external API data, and Cloudflare KV for sub-millisecond suspension flag reads. This module exists in Phase 1 because the entire live betting product is non-functional without it — no DO means no real-time odds, no auto-suspension, and no live scoreboards.

### 7.2 Durable Objects Architecture

Four Durable Object classes are deployed in Phase 1:

1. **MatchDurableObject** — one singleton instance per live match, identified by `match:{matchId}`. Stores current match state (score, market states, live odds snapshot) in DO persistent storage. Manages all WebSocket connections watching that match. Broadcasts score updates, odds changes, and market suspension events to all connected clients simultaneously. Triggers auto-market suspension when a goal (football) or wicket (cricket) event is received.

2. **OddsEngineDurableObject** — one singleton per sport during live periods. Receives raw odds from feed ingestion Workers. Applies margin calculation: `final_odds = raw_odds × (1 - margin%)`. Checks liability before accepting odds update. Writes new odds to KV (`odds:{matchId}:{marketId}`) and calls the relevant MatchDO to broadcast.

3. **BettingSlipDurableObject** — one instance per active user session. Prevents double-submission race conditions by acting as a distributed lock during bet placement. Coordinates the multi-step bet placement flow described in Section 12.

4. **AdminBroadcastDurableObject** — one singleton for the admin panel. Manages all admin dashboard WebSocket connections. Broadcasts: incoming bet flow, risk changes, market suspension events, and live P&L updates.

### 7.3 WebSocket Connection Lifecycle

1. Browser opens `wss://ws.worldgaming.eu.org/match/{matchId}`.
2. Cloudflare Worker validates the `sess_token` cookie against KV.
3. If valid, Worker routes to `MatchDO.idFromName("match:{matchId}")`.
4. Worker calls `do.fetch(upgradeRequest)`.
5. DO accepts the WebSocket via the Hibernation API.
6. DO immediately sends the current `matchState` snapshot as an `init` message.
7. All subsequent score and odds updates are broadcast to all connected sockets from the DO.
8. On WebSocket close or error, the DO cleans up the connection handle.

The Hibernation API is used (not always-active WebSockets) so that DO CPU billing is only incurred during actual message processing, not idle connection holding.

### 7.4 Feed Ingestion Architecture

External data enters the system through two pathways:

**Webhook push (football via SportMonks):** SportMonks posts match events to `https://api.worldgaming.eu.org/webhooks/sportmonks`. The Worker validates the webhook signature, normalises the payload to the internal event schema `{ matchId, sport, eventType, data, timestamp }`, and forwards it to the appropriate MatchDO.

**Polling worker (cricket via EntitySport, tennis/volleyball via API-Sports):** A scheduled Cloudflare Worker polls external APIs on a 5–30 second interval depending on sport and match status. Polling is paused for matches with status `upcoming` more than 30 minutes from start. On data receipt, the same normalisation and MatchDO forwarding pattern applies.

The Feed Normalizer Worker is responsible for:
- Translating all external sport-specific schemas into the unified internal schema.
- Deduplicating events using timestamp + event fingerprint hashing.
- Routing events to the correct MatchDO instance.

### 7.5 Auto-Market Suspension Rules

The MatchDO applies automatic suspension rules without admin involvement:

| Trigger Event | Sport | Action | Auto-Reopen |
|---|---|---|---|
| Wicket fallen | Cricket | Suspend all live cricket markets for this match | After 30 seconds, unless admin manually extends |
| Goal scored | Football | Suspend all football markets for this match | After 60 seconds |
| Set completed | Tennis | Suspend all in-play tennis markets | After 30 seconds |
| Network data gap > 60s | Any | Suspend all live markets for affected match | After data resumes |
| Admin kill switch | Any | Suspend all markets on platform | Manual reopen only |

Suspension state is written to `SUSPENDED_MARKETS` KV namespace with the match ID as key. All bet placement Workers read this KV key as the first step of the validation pipeline — before any DB query — so suspension enforcement adds less than 1ms to the request path.

### 7.6 Odds Update Lifecycle (Timing)

| Step | Time | Action |
|---|---|---|
| T+0ms | External API/Webhook receives new odds |
| T+10ms | Feed ingestion Worker receives event |
| T+15ms | Margin calculation applied: `final_odds = raw_odds × (1 - margin%)` |
| T+20ms | Liability check — if new odds cause liability > max_liability, update rejected |
| T+25ms | KV Write: `odds:{matchId}:{marketId}` → new odds object |
| T+30ms | D1 write to `odds_history` table queued async |

## 8 — FEATURE REQUIREMENTS — WALLET [P0] & LEDGER SYSTEM

### 8.1 Overview

The Wallet and Ledger System is the financial backbone of WorldGaming. It uses a double-entry append-only ledger design — every financial event creates an immutable transaction record with `balance_before` and `balance_after` — ensuring that the sum of all transactions for a user equals their current wallet balance at any point in time. This module is in Phase 1 because no bet can be placed without atomic stake deduction, and no settlement can occur without atomic win credit.

### 8.2 Wallet Record

Each user has exactly one wallet record. The wallet record is the source of truth for current balance. Fields:

- `balance` — main wallet balance (decimal, currency in INR for Phase 1).
- `bonus` — bonus credit balance (tracked separately; not withdrawable).
- `frozen` — boolean flag set by admin to prevent all wallet operations.
- `currency` — `INR` for Phase 1.

### 8.3 Atomic Wallet Operations

All wallet mutations (stake deduction, win credit, deposit credit, withdrawal debit) execute inside a database transaction:

1. SELECT wallet record with row lock.
2. Validate: wallet not frozen, sufficient balance (for deductions), amount positive.
3. Calculate new balance.
4. UPDATE wallet record with new balance and `updated_at`.
5. INSERT transaction record with `balance_before`, `amount`, `balance_after`, `type`, `reference_id`, and `created_at`.
6. COMMIT. If any step fails, the entire transaction rolls back; no partial state is possible.

### 8.4 Transaction Types

| Type | Direction | Trigger |
|---|---|---|
| `deposit` | Credit (+) | Admin approves deposit request |
| `withdrawal` | Debit (−) | Admin approves withdrawal request |
| `bet_stake` | Debit (−) | Bet accepted by system |
| `bet_win` | Credit (+) | Bet settled as win |
| `bet_refund` | Credit (+) | Bet voided or settled as push |
| `cashout` | Credit (+) | User-initiated cashout of open bet |
| `bonus` | Credit (+) | Admin issues bonus credit |
| `admin_credit` | Credit (+) | Manual admin adjustment (credit) |
| `admin_debit` | Debit (−) | Manual admin adjustment (debit) |

### 8.5 Deposit Flow

1. User submits deposit request via the wallet page — enters amount, selects method (informational only in Phase 1; no gateway), optionally attaches a reference note.
2. Deposit request is created in the `deposit_requests` table with `status=pending`.
3. User sees "Your deposit request is under review" confirmation.
4. Admin sees the pending deposit request in the admin Wallet Management panel.
5. Admin verifies payment externally (bank transfer, UPI, etc.).
6. Admin clicks Approve — system executes atomic wallet credit and sets request `status=approved`.
7. Notification is pushed to the user's WebSocket connection: "Deposit of ₹X approved."
8. If admin clicks Reject — request `status=rejected`, user is notified with a reason.

### 8.6 Withdrawal Flow

1. User submits withdrawal request — enters amount and bank/UPI details.
2. System validates: amount ≥ minimum withdrawal threshold (admin-configured), available balance (wallet balance minus stake held in open bets) ≥ requested amount.
3. Withdrawal amount is held (not deducted) — a `pending_withdrawal` field on the wallet prevents double-spending.
4. Withdrawal request created with `status=pending`.
5. Admin reviews and either approves (system deducts from wallet atomically, marks request completed) or rejects (held amount released back to available balance, user notified with reason).

### 8.7 Cashout

1. User clicks Cashout on an open bet from the Betting History or Bet Slip.
2. System fetches current odds for the bet selection.
3. Cashout value calculated: `cashout_value = (current_odds / original_odds) × stake × (1 - cashout_margin)`.
4. If `cashout_value ≤ 0`, cashout is blocked.
5. A cashout confirmation modal shows the calculated value.
6. On user confirmation, wallet is credited atomically, bet `status` updated to `settled`, `outcome` to `cashout`.

## 9 — FEATURE REQUIREMENTS — ADMIN [P0] PANEL (/sgyt)

### 9.1 Overview

The Admin Panel is the operator's control plane, accessible only at the `/sgyt` path. It is protected by four independent security layers before any admin user reaches a functional screen. It is the surface through which all match management, odds management, user management, wallet operations, risk monitoring, and reporting occur. No production change to any user, market, wallet, or match can occur except through this panel or its corresponding API — there is no other write path to the production database.

### 9.2 /sgyt Access Security Layers

1. **Cloudflare WAF Rule (Layer 1):** If `URI path contains /sgyt` AND `IP not in admin_ip_allowlist` → Block (HTTP 403 before hitting the Worker).
2. **Cloudflare Zero Trust (Layer 2):** Cloudflare Access policy applied to `/sgyt/*` requiring email OTP or TOTP from registered admin accounts.
3. **Worker adminGuard Middleware (Layer 3):** Session role must be one of `superadmin | senior_admin | agent | readonly_admin`. Any `user` role session returns HTTP 403.
4. **Admin Session Namespace (Layer 4):** Admin sessions are stored in a separate KV namespace from user sessions. Admin sessions have an 8-hour TTL (shorter than user 24-hour TTL). Admin sessions are invalidated on significant IP change.

## 10 — FEATURE REQUIREMENTS — RISK [P1] & FRAUD ENGINE

### 10.1 Overview

The Risk and Fraud Engine runs synchronously (risk scoring) and asynchronously (fraud analysis) relative to the bet placement flow. Risk scoring runs inline before bet acceptance — it can block or flag a bet before the stake is deducted. Fraud analysis runs asynchronously via Cloudflare Queues so that it does not add latency to the acceptance path. Both systems feed the admin's Risk Dashboard in real time.

### 10.2 Synchronous Risk Scoring

Every bet receives a risk score between 0.0 and 1.0 computed by the Risk Engine Worker before acceptance. The score combines the following factors:

| Factor | Description |
|---|---|
| `stakeVsUserAverage` | Is this stake significantly larger than the user's historical average? |
| `stakeVsMarketLimit` | What percentage of the market's max liability does this bet consume? |
| `oddsValue` | High-odds bets carry higher variance risk |
| `userRecentPnL` | Users on large winning streaks get higher risk scores |
| `userWinRate` | Historical win rate above bookmaker theoretical hold |
| `timeToEvent` | Last-minute bets on live markets are higher risk |
| `marketLiquidity` | Thin markets with few bets amplify individual bet impact |

If `risk_score > 0.7`, the bet is flagged for admin review but still accepted (non-blocking by default; configurable to blocking mode per market). If `risk_score > 0.9`, the bet is held pending manual admin approval.

### 10.3 Per-User Limit Enforcement

Before bet acceptance, the following limits are enforced sequentially. Any failure returns a specific rejection reason to the client:

1. `betting_enabled` flag on user record must be `true`.
2. Bet stake must not exceed `max_bet` for the user.
3. User's total staked amount today must not exceed `max_bet_per_day`.
4. User's total potential winnings today must not exceed `max_win_per_day`.
5. User's allowed_sports must include the sport of the market.

### 10.4 Market Liability Management

- Per-market liability is tracked in real time in KV namespace `MARKET_LIABILITY`: `key: liability:{matchId}:{marketId}:{selectionId}` → `{ totalStaked, totalPotentialPayout }`.
- On every bet placement, KV liability is updated atomically.
- If a new bet would cause total potential payout for a selection to exceed `market.max_liability`, the bet is rejected.
- Liability values are displayed in the admin Risk Dashboard in real time.

### 10.5 Async Fraud Analysis

After bet acceptance, the bet is published to the `fraud-analysis-queue`. The Fraud Analysis Worker processes it asynchronously and writes fraud flags to the `fraud_flags` table. Fraud detection rules:

- **Matched betting detection** — Bets placed across correlated selections in close time proximity on the same market (betting both sides).
- **Syndicate detection** — Multiple user accounts with the same device fingerprint or IP placing similar bets simultaneously.
- **Sharp bettor identification** — User win rate consistently exceeds the theoretical hold by more than 2 standard deviations over 30+ bets.
- **Unusual stake spike** — Stake is more than 5× the user's 30-day average without prior history of large stakes.

Fraud flags are surfaced in the admin Risk Dashboard and flagged bets queue. Admins can dismiss flags, void bets, or take user management action directly from the flag detail view.

| 5 | System | KV write | `odds:{matchId}:{marketId}` updated with new odds and timestamp |
| 6 | System | D1 write queued | `odds_history` row inserted async |
| 7 | System | MatchDO called | MatchDO broadcasts odds update to all connected user WebSockets |
| 8 | Users | Receive update | Odds on BET-03/04/05/06 flash green or red; Bet Slip payout recalculates |
| 9 | Admin | Sees updated odds on ADM-04 | Odds movement log entry appears in real time |

## 13 — STRATEGIC DIFFERENTIATORS

| # | Differentiator | Gap Closed | Competitor Status |
|---|---|---|---|
| 1 | **Cloudflare Durable Objects per-match WebSocket hub** | Eliminates centralized WebSocket bottleneck; 50,000+ concurrent connections per live match auto-scale without pre-provisioning | All major competitors use Node.js clusters or Redis pub/sub requiring manual scaling and infrastructure management |
| 2 | **Opaque KV session tokens with instant revocation** | Admin can ban or suspend a user and their access is revoked on the next request (~1–2 seconds) with no JWT residual window | JWT-based platforms have 15-minute revocation lag; PHP session platforms require Redis flush scripts |
| 3 | **Admin-provisioned accounts only with per-user risk limits** | Operator maintains complete control over who can bet and how much; no anonymous sign-ups | Most platforms allow self-registration; per-user limit configuration requires admin UI that most white-label panels lack |
| 4 | **Atomic double-entry ledger** | Every balance mutation is transactionally consistent; `SUM(transactions.amount) = wallet.balance` verifiable at all times | Script-based panels update balance with non-transactional `UPDATE balance = balance - stake` calls vulnerable to race conditions |
| 5 | **Sub-50ms odds delivery from edge** | Users on any continent receive live odds changes in under 50ms via DO broadcast; no polling required | Polling-based platforms (30–60 second refresh intervals) create stale odds arbitrage opportunities and poor UX |
| 6 | **4-layer /sgyt admin access protection** | Admin panel is invisible to non-whitelisted IPs at the WAF layer before any Worker code runs | Standard panels rely on a single username/password login with no IP restriction or Zero Trust identity gate |
| 7 | **Cloudflare-native full-stack — zero VM management** | Entire platform runs on Cloudflare Workers, Pages, KV, DO, Queues, R2, and D1; no server provisioning, no load balancers, no autoscaling groups | All enterprise competitors require VMs, cloud load balancers, and infrastructure management; script panels require shared hosting |
| 8 | **Auto-market suspension on in-play events** | Markets suspend within 50ms of a goal or wicket; no admin action required | Competitors require manual admin intervention or expensive real-time rule engines; PHP panels have no auto-suspension |

## 20 — OPEN QUESTIONS AND DECISIONS

| ID | Question | Context |
|---|---|---|
| OQ-01 | Should PlanetScale or Cloudflare D1 be used as the primary database for Phase 1? | D1 is simpler to deploy but has a ~100 writes/second ceiling and ~100–200ms write latency for non-primary-region Workers. PlanetScale has higher write throughput and global read replicas but requires the `@planetscale/database` HTTP driver. The decision affects bet placement latency and scaling headroom. Default recommendation: PlanetScale for financial tables, D1 for reference data. This must be decided before database schema migration scripts are written. |
| OQ-02 | What is the admin IP allowlist for the /sgyt WAF rule? | The WAF rule blocking /sgyt from non-admin IPs requires a known set of static IPs. If the operator's admin team works from dynamic IP addresses (e.g., home connections, mobile data), Cloudflare Zero Trust (Cloudflare Access with email OTP) must be the primary gate and the IP rule must be relaxed or removed. This must be decided before production WAF rules are deployed. |
| OQ-03 | What is the cashout margin percentage? | The cashout formula includes `(1 - cashout_margin)`. This is a business decision, not a technical one. The default in the research is unspecified. A margin of 5–10% is typical. This value must be confirmed before the cashout feature is deployed so that it is correctly reflected in the user-facing confirmation modal. |
| OQ-04 | Should bets with risk_score > 0.7 be blocking (rejected) or non-blocking (flagged but accepted) by default? | Non-blocking (accept and flag) is recommended for Phase 1 to avoid false positives that hurt user experience during platform calibration. However, some operators prefer blocking high-risk bets above a configurable threshold. This must be decided as a configurable platform setting in ADM-18 before go-live. |
| OQ-05 | What is the minimum withdrawal amount and the withdrawal processing SLA communicated to users? | The minimum withdrawal amount must be set in admin settings (default suggestion: ₹500). The SLA (e.g., "withdrawals processed within 24 hours") must be agreed with the operator and reflected in the user-facing withdrawal flow. |

## 21 — GLOSSARY

| Term | Definition |
|---|---|
| **Accumulator / Parlay** | A multi-selection bet where all selections must win for the bet to return a profit; combined odds are the product of all individual selection odds |
| **AdminBroadcastDO** | The AdminBroadcast Durable Object — a singleton per platform that manages WebSocket connections for all admin dashboard sessions and broadcasts live bet flow and risk events |
| **Argon2id** | The OWASP-recommended password hashing algorithm used in WorldGaming; memory-hard, combining GPU-resistance (Argon2d) and side-channel resistance (Argon2i) |
| **BettingSlipDO** | The BettingSlip Durable Object — one instance per active user session; acts as a distributed lock to prevent double-submission race conditions during bet placement |
| **Cashout** | A feature allowing a user to settle an open bet before the market result is known, in exchange for a guaranteed partial return based on current odds |
| **D1** | Cloudflare D1 — a SQLite-compatible relational database running at the Cloudflare edge, used for reference data, audit logs, and low-write-volume tables |
| **Durable Object (DO)** | A Cloudflare compute primitive providing strongly consistent, stateful singleton JavaScript objects with built-in WebSocket support; used in WorldGaming for per-match WebSocket hubs |
| **Feed Normalizer Worker** | A Cloudflare Worker that translates all external sports API payloads into the unified internal event schema `{ matchId, sport, eventType, data, timestamp }` |
| **GGR** | Gross Gaming Revenue — total stakes received minus total winnings paid out, before operating costs |
| **Hono** | A lightweight TypeScript web framework designed for Cloudflare Workers; used as the API layer in WorldGaming |
| **HttpOnly cookie** | A browser cookie attribute preventing JavaScript access; used for `sess_token` so that XSS attacks cannot steal session tokens |
| **KV (Cloudflare KV)** | Cloudflare's key-value store used in WorldGaming for sessions, odds cache, market suspension flags, rate limit counters, and market liability |
| **Kill Switch** | The admin control that suspends all open markets across all sports platform-wide simultaneously; available on ADM-18 Admin Settings |
| **Liability** | The total maximum payout the platform would owe if all currently open bets on a selection or market win simultaneously |
| **Market** | A specific betting proposition within a match (e.g., "Match Winner", "First Innings Runs", "Over 2.5 Goals"); a match can have multiple markets |
| **MatchDO** | The Match Durable Object — one singleton per live match that manages all WebSocket connections watching that match and broadcasts score and odds updates |
| **NGR** | Net Gaming Revenue — GGR minus bonuses paid and any applicable payment processing fees |
| **Opaque session token** | A random, meaningless string used as a session identifier; stored in Cloudflare KV; the client cannot decode it to determine any user information |
| **Overround / Margin** | The bookmaker's built-in profit margin; if all selection probabilities implied by the odds sum to more than 100%, the excess is the overround |
| **PlanetScale** | A MySQL-compatible serverless database with horizontal sharding via Vitess; used as the primary financial database in WorldGaming via its HTTP driver compatible with Cloudflare Workers |
| **Selection** | An individual outcome within a market that a user can bet on (e.g., "India", "Draw", "Pakistan") with an associated odds value |
| **Settlement** | The process of evaluating an accepted bet against the final market result, crediting winnings, or recording a loss after a match is completed |
| **/sgyt** | The hidden URL path serving the WorldGaming admin panel; chosen to be non-obvious to reduce attack surface; blocked at WAF for non-admin IPs |
| **SUSP badge** | The visual indicator shown on a market or selection when its status is `suspended`; users cannot add suspended selections to their bet slip |
| **Wrangler** | The Cloudflare CLI tool used to deploy Workers, Pages, and D1 migrations; used in the GitHub Actions CI/CD pipeline |
| **Zod** | A TypeScript-first schema validation library; all API request bodies in WorldGaming are validated with Zod before reaching any business logic or DB query |
